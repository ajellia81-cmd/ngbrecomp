# True 120 fps: code audit and remaining implementation

The requested result is 120 different, newly rendered scene frames per second,
with original game speed/physics. Repeating a 60 fps image, raising a display-link
rate, or relabeling a presentation counter does not meet it. No true-120 option
is implemented or advertised in the current IPA.

## Verified coupling in this repository

- `xboxrecomp/src/nv2a_vk/host/nv2a_host.c`: `s_refresh_hz` defaults to 60;
  `vblank_thread()` raises the guest CRTC interrupt and drives flip scheduling.
  `NV2A_REFRESH_HZ` is a test override, not a physics-correct FPS patch.
- `src/d3d/hle.cpp`: `D3DF_D3DDevice_Swap` calls the host backend's `Present()`.
- `src/d3d/vk/backend.cpp`: `Draw()` consumes the current guest state and mutable
  vertex/index sources. `Present()` copies the completed target into a display
  image and resets per-frame renderer/HUD state. It does not retain a complete
  immutable scene packet that can be rendered at another time.
- `gpu::State` has 512 transformation matrices and 192 vertex-constant vectors,
  with resource references and shared shader objects. `gpu::Assembled` still
  contains raw pointers to guest vertex/index data. Copying `State` alone is not
  a safe frame snapshot.
- Private inspection of the owner's USA executable identified the main loop at
  `0x0030E140`, swap paths at `0x0030CC50`/`0x0030CDB0`, and vblank waits through
  `0x00332D50`. The frame counter at `0x00D21734` is referenced by 105 generated
  functions. These are not all proven physics sites; they demonstrate that
  doubling loop frequency requires a game-wide timing audit.

An iOS log now records **guest Swap rate**, using virtual foreground time. That
is useful baseline data but is not proof of 120 distinct frames or GPU headroom.

## Rendering 120 while preserving 60 Hz game simulation

The preferred route is a real renderer decoupling, similar to interpolation in
other static recompilation projects, rather than executing game updates twice:

1. Capture an immutable render packet for each completed 60 Hz update: draw
   order, clear/copy passes, material/shader state, vertex/index data, transforms,
   bone/animation data and versioned resources. Mutable guest pointers cannot
   survive as the packet's only storage.
2. Match stable object/draw identities between consecutive snapshots. Interpolate
   camera and object/bone transforms for two render instants. Do not interpolate
   every raw shader constant: constants also contain flags, lighting and other
   values that require their own interpretation. Reject matching across cuts,
   teleports, load transitions, spawn/despawn and changing topology.
3. Replay the entire 3D render graph for each instant, including depth, shadows,
   offscreen effects and HUD policy. This produces different rasterized scenes;
   copying/reprojecting one finished color image would be a different feature.
4. Pace scene renders at 8.33 ms on a supported display while keeping the guest
   interrupt/update clock at 16.67 ms. Input latency, buffering and interpolation
   latency must be measured. Background pause applies to both loops.

The other route, 120 game updates, requires explicit conversion of frame-based
movement, animation, AI, invulnerability/collision windows, input repeat and timers
to a valid 1/120 timestep. Neither a global half-speed clock nor a blanket change
from 60 to 120 is sufficient evidence of equivalent behavior.

## Completion gates, not yet passed

- Implement the packet ownership/replay and transform interpolation paths.
- Verify different scene states and independently rendered frames, not only
  acquire/present calls or display refresh rate.
- Measure CPU/GPU frame budgets on the owner's device, both at 1x and native
  resolution. A 120 Hz screen does not establish an 8.33 ms renderer budget.
- Compare repeatable 60/120 runs: movement distance, jump/attack durations, enemy
  behavior, collision windows, timers, cutscenes and save/load outcomes.
- Test Korean fonts, native-resolution targets and background/resume with the
  new render loop. Those combinations have not been verified.

These are substantive renderer/game changes still required; the current build
does not satisfy the owner's true-120-fps request.
