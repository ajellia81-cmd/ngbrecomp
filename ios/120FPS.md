# Experimental iOS Smooth Motion

The iOS renderer now has a real intermediate-scene replay path targeting a 120 Hz
display while retaining the original 60 Hz guest vblank, simulation, audio and
visibility-query behavior. This is an implementation, not a measured claim of
sustained 120 fps on the owner's phone. Previous downloadable builds before this
change do not contain it.

## Implementation

1. Render the authoritative guest frame normally. Retain owned vertex/index
   bytes, uniform data, pipeline/descriptors and the ordered clear/draw/copy
   recipes. Immutable GPU texture versions remain alive until `EndFrame`.
2. Retain the previous matching draw's vertex constants and fixed-function
   transforms. Match geometry/layout/index/material/pass keys and occurrence.
   Geometry whose bytes or topology change does not inherit an unrelated pose.
3. The intermediate vertex shader evaluates the original shader separately with
   previous and current constants, then interpolates clip positions and vertex
   outputs at the midpoint. Integer selectors and arbitrary shader constants are
   never averaged. Fixed-function transforms and programmable bone/camera
   constants both use this path. Large projected jumps and projection sign
   changes reject interpolation per vertex.
4. Snapshot initial single-sample color/depth inputs directly into isolated
   replay targets. Replay the supported clear/draw/copy graph there, including
   mapped target feedback copies, shadow inputs and descriptors. Authoritative
   targets remain untouched; there is no final-state backup/restore roundtrip.
5. Submit original and midpoint commands in order on the shared Vulkan queue.
   A latest-pair worker presents midpoint and endpoint at display cadence.
   Its bounded mailbox never waits for display cadence on the guest thread;
   active images retain leases until their GPU copy fences finish. Pending
   older pairs can be replaced. The guest does not sleep for 8.33 ms or wait
   for two swapchain acquisitions. Midpoint/endpoint buffers rotate separately.
6. If two guest Swap intervals exceed 25 ms while replay was used, suspend
   replay for 120 guest frames, then retry. This preserves ordinary gameplay
   priority when there is insufficient rendering headroom; it does not lower
   the selected resolution or double the simulation clock. Submitted worker
   counts are logged separately from offered pairs and guest swaps.
7. Boot movies and 2D/title menus bypass midpoint replay. Normal and pair
   producers publish each image together with its dimensions under the same
   presentation lock; individually atomic fields are insufficient for this tuple.
   Fresh replay depth targets retain the original clear/LOAD state, and the replay
   pass ends before its final composite.


This is vertex-output interpolation, not a finished-image blend, optical-flow
postprocessing, or a global game-speed change. A static scene may legitimately
produce identical pictures. Cuts, missing matches, shader-cache misses, loading,
resize and unsupported graphs can skip intermediate scenes.

`src/d3d/gpu/motion.h`, `src/d3d/vk/motion_replay.inc` and the backend's capture
points implement the path. The shader cache uses a separate variant key. Owned
packets have a 96 MiB cap; target snapshots have a conservative 256 MiB cap.
Oversized packets, target replacement and allocation failure invalidate replay
without substituting a partial graph. Each draw reserves one upload-ring
generation for its uniforms and geometry. Each of the two frame slots is
**32 MiB** inside the 64 MiB allocation: reservations use the slot boundary used
by Upload(), not the whole allocation. Slot-tail, crossing, oversize and arithmetic
overflow cases are checked in the retained-pose test.

## Settings and first test

- iOS Recomp Settings → Display & Audio → **Smooth Motion: On** (default on).
- **MSAA: Off** and **Smoother Glow: Off**. Custom glow-filter paths and MSAA do
  not yet have complete replay recipes, so they retain normal rendering.
- Start at **1x** before testing native resolution. No scale governor silently
  changes the selected quality. GPU headroom at native resolution is unknown.
- A CADisplayLink requests the screen's maximum supported rate. Its reported
  display interval gates replay; below 100 Hz the renderer uses normal rendering
  to avoid halving game speed on a 60 Hz display or under system rate limits.
- Lifecycle epoch changes and long gaps clear history. Resize/quality changes
  invalidate captured resource identities. Game data and Korean text selection
  use the existing paths; no ISO/archive re-upload is needed.

`[Smooth Motion]` logs actual submitted midpoint-scene counts, matching candidates,
packet/snapshot sizes, eligibility, MSAA/glow and display cadence. `[iOS FPS]`
counts guest swaps separately. Neither counter alone proves unique on-screen
pictures, correct motion across the game or sustained 120 fps.

## Verified and remaining

Local C++ compilation covers feature-on iOS declarations and the feature-off
renderer. Synthetic retained-pose tests cover ownership, changed poses, new
geometry rejection and history reset. GitHub's macOS job compiles the actual
fixed/program vertex variants to SPIR-V with glslang, and checks settings and
runtime regressions. `python3 ios/presenter_descriptor_test.py` extracts the
actual production publication functions into a blocked-presenter/thread test: the
serialized version passes and the unlocked negative control is rejected. It does
not test GPU rasterization. The [complete Actions run](https://github.com/ajellia81-cmd/ngbrecomp/actions/runs/40200373376)
passed both jobs, including full iPhoneOS ARM64 engine link and encrypted game IPA
packaging. Build source is `e4f37dc34106ad08ebd708b94a71cac4e906d562`.

Device validation is still required: image/depth/shadow correctness, geometry
matching under reordered draws/spawns, Korean fonts, lifecycle resume, sustained
8.33 ms budgets, input latency, and identical movement/combat/timer behavior.
Changed vertex buffers currently fall back rather than interpolate CPU-deformed
geometry. Matching uses draw identity/occurrence, not game-level actor IDs; camera cuts require whole-frame history reset; complete cut detection is not implemented.
There is no physical-device or full-game headless replay result for this change:
the cloud has the build XBE, but not the complete game archives needed for such a
run. No game data or generated game C is committed.

## Virtua Fighter Smooth Motion reference (owner request)

Reviewed the owner's iOS branches in cloud checkouts, without running their games
or modifying those repositories. Pinned references:

- [VF1 model1_interp.cpp](https://github.com/ajellia81-cmd/vf1-recomp/blob/944b1ebf6b21b303b82ca46c5e198a30b92e6d55/src/machine/model1_interp.cpp):
  `record_frame()` retains display lists; `index_objects()` identifies matrix slots;
  `blend_slots()` matches slots and interpolates transforms. Rotation uses quaternion
  slerp, with translation/scale interpolation. Cuts and unmatched objects have
  explicit fallback policies. The original game clock is unchanged.
- [VF2 model2a.cpp](https://github.com/ajellia81-cmd/vf2-recomp/blob/a6f6dc5aec8cc5247594766618fe2ce6633f1b97/src/machine/model2a.cpp):
  `render_smooth(alpha)` redraws between retained geometry frames. Changed RAM is
  tracked so an earlier frame can retain its own colours; 2D is cached separately,
  and backdrop scroll is matched to the interpolated camera.
- [VF3 r3d_scene.cpp](https://github.com/ajellia81-cmd/vf3-recomp/blob/a8473a99091e6bb207c85d6d247eece8c4866b39/src/video/r3d_scene.cpp)
  and [host/main.cpp](https://github.com/ajellia81-cmd/vf3-recomp/blob/a8473a99091e6bb207c85d6d247eece8c4866b39/src/host/main.cpp):
  `Scene` owns viewports/models and shared mesh data. `interpolate()` pairs models
  by viewport, address/path and geometry, caches pairing for a scene pair, blends
  matrices and compatible vertices, and rejects cuts. `draw_picture()` passes the
  resulting scene to the raster/GPU preparation path. These are newly rendered
  intermediate scenes, not merely repeated finished pictures.

This is a directly relevant rendering architecture for the requested result:
keep NGB logic at 60 Hz and rasterize intermediate 3D states at display cadence.
It introduces interpolation latency (typically one game-frame interval) and does
not guarantee every picture differs during static scenes, pauses or camera cuts.
The iOS reference repositories themselves distinguish their implementation from
measured sustained 120 fps on a physical phone.

### Concrete NGB adaptation boundaries

1. `VulkanBackend::Draw()` currently calls `Assemble()` and records GPU work
   immediately. Add an owned render-packet boundary here. Copy/index the actual
   vertex/index bytes and retain shader/resource versions, not guest addresses.
   A copy of `Assembled` alone still contains guest buffer/index pointers.
2. Retain the ordered `Clear`, `Draw`, `Copy`, and target/texture version changes
   through `Present`. Offscreen render targets are part of the frame, so replaying
   only final-target draws cannot reproduce shadows and effects correctly.
3. Match stable draw/object identities (geometry/material/pass plus occurrence,
   with conservative rejection) and identify actual transform/bone constants.
   VF's Model 1/2/3 matrix formats cannot identify NGB's Xbox shader constants.
   VF3's all-element matrix lerp is not a universal replacement for VF1's slerp;
   select interpolation according to the transform representation.
4. Render the retained graph at intermediate timestamps, with original HUD/text
   policy and cut/load/spawn rejection. Keep guest vblank, audio and simulation
   scheduling at 60 Hz. Reset frame history on resize, language boot, lifecycle
   transitions and device/resource invalidation.
5. Validate frame ownership after guest mutation, stable pairing/cut rejection,
   midpoint geometry/depth/shadows, unchanged 60 Hz gameplay, and 8.33 ms device
   CPU/GPU budgets. Counter-only presentation tests do not establish distinct
   rasterized scene states.

The review above informed the new replay path documented first. VF scene formats
were not copied into NGB; no VF source code was copied. The remaining limits
apply to this experimental implementation, even when compilation succeeds.


The old synchronous replay/presentation path had a device report of half-speed
normal gameplay. The isolated-target/worker path above replaces it. A successful
compile is not evidence that this device regression is resolved: retest gameplay,
cutscenes, frame rates and pause/resume on the same phone after updating.

## Reading the iOS counter

The original FPS overlay counted only guest flips, which remain 60 Hz even when
intermediate pictures are presented. When the worker successfully submits
midpoint/endpoint pairs, the iOS overlay now reports their measured picture rate
and the separate game rate (for example, `120 FPS game 60`). Failed or superseded
pictures do not increase this pair count. Without successful midpoint output,
the ordinary game-frame counter remains. This display correction is not proof
that any particular phone sustains 120 FPS. Eligibility diagnostics now record
the request, shared queue, scene draws, 2D/movie/menu state and cooldown alongside
existing match, memory, MSAA, glow and measured display-cadence information.

To diagnose a remaining 60-FPS report, record a foreground gameplay session with
Smooth Motion enabled and movement for at least ten seconds, then copy the
current `Documents/saves-korean/log.txt` (or the path in build-info.txt). Title,
settings and movie screens deliberately use the original rendering path.
Long New Game loading and sustained output performance remain device-test items.

## Device output bottleneck seen in 2.41

The owner's 120-Hz session queued about 300 midpoint/endpoint pairs per five
seconds, while the worker completed only about 150 pairs and superseded the
others. Thus the renderer produced intermediate scenes but delivered about 60
pictures per second. The new presenter does not hold the shared GPU queue mutex
while waiting for a swapchain image; acquisition is serialized by its existing
present mutex. It waits for the final successful pair-copy fence once per pair,
not after the midpoint as well. The final wait also covers an unsuccessful
endpoint acquisition so the midpoint source remains leased until its copy ends.
A production-worker test checks both success and failed-endpoint paths and
rejects a missing-fence negative control. This is a lifetime/pacing test, not a
phone throughput benchmark. New pacing logs separate pair time, drawable wait
and final copy wait if output is still limited. Sustained native-resolution
120 FPS remains unverified until the owner retests.


## 2.48 device-log follow-up

The owner confirms that 2.47 boots into gameplay and Korean text is now correct.
Its subsequent log still shows mean pair service times of 27–30 ms, repeated
120-guest-frame overload cooldowns, and sparse midpoint output despite a 120 Hz

Metal encoding to MoltenVK's ordered dispatch queue while retaining Vulkan queue
external synchronization and fence-based image leases. The iOS swapchain requests
three drawables within the device's advertised bounds. The presenter now reports
lock, submission and presentation time separately, in addition to acquisition
and copy-completion waits. The existing overload guard and 60 Hz simulation are
retained. Test a moving 3D gameplay scene; static menus and movies bypass replay.
A successful device build does not establish sustained 120 distinct frames.


## Camera-motion correctness (2.51)

The owner reports continued 60 FPS and camera-dependent wall flicker on 2.48.
The vertex-level NDC-distance cutoff could select endpoint vertices and midpoint
vertices in the same primitive. It is removed so finite homogeneous clip
positions interpolate consistently before clipping, including near-plane and
offscreen vertices. This corrects a shader defect; the reported wall flicker
still needs device verification and a Smooth Motion On/Off comparison. Native
font orientation is separately checked with the actual CoreText function on the
macOS runner. Neither change establishes a sustained 120 FPS performance result.


## 2.51 measured submission rate and counter build flags

The owner's 2.48 gameplay log records 300/301 pairs per approximately five seconds
in several windows, around 120 submitted midpoint/endpoint pictures per second.
Mean pair service is 12–17 ms after asynchronous Metal encoding and triple
buffering; occasional backpressure and an overload cooldown remain. Off removes
the reported wall flicker, tying it to replay. The coherent clip-space interpolation
correction needs a device retest.

The overlay's iOS output accounting used NGB_IOS_APP, defined on the executable
and D3D backend but absent from the runtime library compiling present_sdl.c.
The platform guard now uses __APPLE__/TARGET_OS_IPHONE. A regression fixture
runs the actual sampler at 60 guest flips and 120 submitted pictures per second
without the app define, verifies the two rates separately, and tests menu and
desktop fallback. The old guard fails the same fixture. Successful fenced pair
copies establish submission/completion counts, not physical drawable presentation
timestamps. Sustained, distinct and visually correct 120 Hz scanout across the
game is still not independently verified.


## 2.54 precision and device status

The owner confirms 120 FPS operation in 2.51 but still observes polygon-face
flicker during camera motion, disappearing with Smooth Motion Off. The
per-vertex-cutoff change did not resolve it. The interpolation helper now marks
its subtract/multiply/add precise so layered EQUAL-depth passes do not acquire
contraction/reassociation differences. CI compiles the actual helper to SPIR-V,
verifies NoContraction on each operation, and rejects the unprotected control.
The fixed and programmed full vertex shaders are also compiled. This is compiler
validation; device correctness is still pending. EQUAL-depth draw counts are
logged. The new controller-only haptic worker and image lettering are independent
of geometry timing, and the original guest simulation remains 60 Hz.
